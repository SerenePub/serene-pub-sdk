# 03 — Extension System

**Status:** Consolidated 2026-08-17. Implements Constitution §3, §9–§12, F2, F10–F11, F17–F19,
F27. Scope: what an extension *is* — manifest, runtimes, communication, hooks and exports,
storage. **Distribution, permissions and lifecycle moved to 09-PLUGIN-LIFECYCLE. UI moved to
10-COMPONENTS.**

## 1. Plugin, extension, component

**Plugin** is the umbrella term for a distributable package. Three types, mixable in one package:

| Type | Contributes | Has a backend? |
|---|---|---|
| **Extension** | pipeline types (Query/Task/Provider/Consumer bindings), hooks, exports | yes |
| **Component** | UI surfaces | **no** — static/front-end only, no side effects |
| **Pipeline bundle** | statically exported specs | no |

Hybrids are the norm. The `match` mechanism (§6) unifies "backend extension ships with UI"
without the two halves coordinating through anything but data.

**A component-only plugin has no backend, therefore no socket handlers.** It renders and calls
`public.core`; nothing more. Components needing custom server data ship alongside an extension.
Not obvious from "components are their own type," and authors hit it immediately.

## 2. Manifest

```jsonc
{
  "id": "chariot.dice-tray",
  "version": "1.2.0",
  "engines": { "serene-pub": ">=0.6 <0.8" },
  "sdk": { "minimum": "0.6.0" },
  "runtime": { "kind": "node", "entry": "dist/server.js" },
  // or: { "kind": "process", "command": ["uv","run","main.py"],
  //       "protocol": "jsonrpc-stdio@1" }
  "adminOnly": false,
  "managesOwnCredentials": false,
  "contributes": {
    "pipeline":   [{ "type": "task", "id": "chariot.dice-tray:roll@1" }],
    "specs":      "dist/specs/",              // static export dir (F27)
    "components": [ /* see 10-COMPONENTS §3 */ ],
    "hooks":      [{ "id": "startup", "cadence": "startup" },
                   { "id": "nightly", "cadence": "cron", "expr": "0 3 * * *",
                     "overlap": "skip", "budget": { "tokens": 50000 } }],
    "exports":    [{ "id": "rollFormula@1", "public": true }],
    "events":     { "emits": ["chariot.dice-tray:rolled@1"] },
    "settings":   "schema.json"
  },
  "dependencies": { "chariot.tables": "^2.1.0" },   // runtime, must be installed
  "libraries":    { "chariot.dice-lib": "^1.0.0" }, // build-time, vendored
  "permissions": [ /* generated by the SDK packager — 09 §4 */ ]
}
```

- **Generic over registries.** `contributes` keys map to open registries; adding a registry later
  is additive — no schema migration, no loader change.
- **`dependencies` vs `libraries` are different concepts and must not share a name.**
  Dependencies are runtime, must be installed on the instance, and are reached through
  core-brokered exports. Libraries are build-time and vendored into your bundle.
- **Everything declared is enumerable** → the load-time audit view and the install-time capability
  display are SELECTs, not scans.
- Full field list, release rules and verification: 09-PLUGIN-LIFECYCLE §2–§3.

## 3. Backend runtimes and dependencies

| | `runtime: node` | `runtime: process` (sidecar) |
|---|---|---|
| Loading | prebuilt ESM, host imports | host spawns `command`, JSON-RPC over stdio |
| Call cost | direct async, zero serialization | one RPC hop |
| Dependencies | **bundled at plugin build**, per platform; externalize only `@serene-pub/sdk/*`; no runtime npm install | **bundled at plugin build**, per platform — vendored wheels, a zipapp, or a compiled binary. Not a `pyproject.toml` the host resolves |
| Native modules | not supported → use sidecar | fine |
| DB | injected scoped APIs only | **no channel exists** (F19) |
| Consumers | may receive transaction-scoped commit API | strictly functional: return commit description, core applies |
| Streaming | native | **`jsonrpc-stdio@1` must define stream chunks as notifications**, or transport becomes a behavioural difference rather than a routing detail |

**The host is never presumed to have anything (F33).** A plugin ships what it needs for each
platform it declares, so "works on my machine" is not a category of bug that can reach a user.
Consequences: artifacts are genuinely per-platform rather than nominally so, the platform matrix in
the manifest becomes load-bearing, and **an unsupported platform is refused at install with a
clear message** rather than discovered when a node first runs.

Two escape valves, both *checked* rather than presumed:

1. **Declare a host requirement** it cannot reasonably vendor (a GPU runtime, a multi-hundred-
   megabyte native stack). SP verifies it at install and refuses cleanly if absent.
2. **Fetch a dependency** on startup or on demand, into the plugin's own data directory. Ships
   small, pulls heavy things on first use.

### ⚠ Fetched dependencies must be declared and checksummed, or the verification chain means nothing

The release standard (09 §3) is a chain: tag → commit → manifest → artifact checksum → stored
manifest hash → every runtime permission check. **A startup hook that pulls a binary from an
arbitrary URL walks straight around all of it.** The plugin an admin reviewed and the code that
ends up executing are then different things, which is precisely the property the chain exists to
prevent.

So a fetched dependency is a manifest entry, not an implementation detail:

```jsonc
"fetchedDependencies": [
  { "id": "onnx-runtime", "url": "https://…/onnxruntime-linux-x64.tgz",
    "sha256": "…", "bytes": 412000000, "when": "on-demand",
    "platforms": ["linux-x64"] }
]
```

- **Checksum verified on fetch.** A mismatch fails the fetch and disables the plugin with a
  diagnosed reason, exactly like a missing file (09 §7).
- **Declared, so it is visible at install** — *"this plugin will download ~400 MB from example.com
  on first use"* — alongside permissions and bundle size. An admin should never be surprised by a
  network fetch.
- **Requires the `net` capability** for that host, granted like any other permission (F28).
- **Offline and failure behaviour is defined:** a failed fetch is a diagnosed broken state, never a
  silent degradation or a retry loop.

Un-declared runtime fetching of executable code is a non-goal (01 §16).

- Transport is a `type_registry` column; the executor is indifferent.
- **No per-plugin loopback HTTP servers** — port allocation, per-plugin auth, and a firewall
  prompt per plugin that bench customers will click Deny on. Stdio has none of that.
- Sidecar lifecycle: spawn, health-check, restart policy, kill on cancellation. Budgets meter its
  reported consumption; waiting is free.
- **Timeouts at three levels** (F36): **per call** (this RPC, wall or idle depending on whether the
  shape streams), **per process** (a health check that stops answering triggers restart), and an
  **idle shutdown** so an unused sidecar does not linger holding memory. All three are declared
  with descriptor defaults, config overrides and an admin ceiling.
- **A sidecar timeout is a real kill.** This is the one place enforcement is absolute — the process
  is terminated. It is worth telling plugin authors plainly: if your work can hang, `runtime:
  process` is the transport that can actually stop it.

## 4. Communication topology (core owns every transport)

- **Plugin backend ↔ plugin backend:** no direct transport. Composition is dataflow (edges in a
  spec), events (11-EVENTS), or **exports** (§5) — all brokered by core.
- **Plugin backend ↔ core:** in-process → injected capability-scoped host API; sidecar → the
  bidirectional stdio channel.
- **Plugin UI ↔ plugin backend:** namespaced channel over SP's existing WebSocket layer under
  `plugin:<id>:<descriptor>`. **Extensions never write handlers** — they declare them, and core
  registers and forwards. See 10-COMPONENTS §5; the security consequence is that identity and
  permission checks have no path around them.
- **REST carve-out:** a single host-owned mount at `/api/plugins/:id/*`, declared as a capability —
  media URLs, file upload/download, OAuth callbacks. Never a plugin-owned server. Inbound
  webhooks do not terminate in plugin code: the host endpoint receives, authenticates, and
  surfaces the event as pipeline input.

## 5. The three hook kinds

Everything an extension exposes is a hook; core invokes all of them. Full rules in 01 §9.

| | **Pipeline hook** | **Lifecycle hook** | **Event hook** |
|---|---|---|---|
| What it is | a node type's implementation | core-invoked at defined moments | registered against a core event |
| Invoked | by the executor, mid-run | on load, startup, shutdown, enable, disable, update, sidecar spawn, or a schedule | when the event occurs |
| Visible in the spine | **yes** | no | no |
| Observability | full receipt | invocation record | invocation record |
| Public? | **private or public** — public means any spec may pin it | never | never |
| May call Providers | yes | yes, within its budget | **no** (F32) |
| **Timeout** | **required** (F36) | **required** | **required** |

```jsonc
"hooks": [
  { "kind": "pipeline",  "id": "chariot.dice-tray:roll@1", "node": "task", "public": true },
  { "kind": "lifecycle", "id": "startup", "cadence": "startup" },
  { "kind": "lifecycle", "id": "nightly", "cadence": "cron", "expr": "0 3 * * *",
    "overlap": "skip", "budget": { "tokens": 50000 }, "timeoutMs": 600000 },
  { "kind": "event",     "id": "onChatCreated", "event": "core:event/chat-created@1",
    "timeoutMs": 5000 }
]
```

- **Public pipeline hooks are the peer-composition mechanism**, and they replace the former
  "export" concept entirely (01 §9b). Another plugin uses your hook *as a node in its spec*, so
  the dependency is a pin, the call is a step on the spine, and the receipt records it. Nothing is
  invisible, so nothing needs banning.
- **Scheduled lifecycle hooks declare cadence, overlap policy (default skip), their own budget and
  a timeout.** Without a budget, an hourly hook making Provider calls is unbounded spend nobody
  authorized; without a timeout, one stuck invocation holds the skip-lock forever and the hook
  silently never runs again. **A timed-out invocation releases its lock**, which is the detail that
  makes overlap policy survive contact with a hang. Missed firings are never backfilled on
  re-enable.
- **Event hooks may not call Providers** (F32). They exist for the light case — maintaining the
  extension's own data when something happens — and they run outside the run model, so they get no
  receipt, no replay and no review gate. Anything needing a model call triggers a *pipeline*
  instead, which brings all three with it. Author guidance in 01 §9c.
- **A hook that starts a run is that run's root cause.** Receipts record
  `trigger_source = hook|schedule|event` and `trigger_ref`, or background work is unattributable
  in the run inspector.
- **Arbitrary hook code is opaque, symmetrically** (01 §12.3). Core sees the inputs, the invocation
  time and the return value. Unrelated side effects hidden in a Consumer's pipeline hook are a
  **social** violation policed by removal from the official list, not a technical one — say so
  plainly in the publishing guidelines, since the docs otherwise imply everything is mechanically
  enforced.

## 6. The `match` mechanism

A plugin's Task emits a message carrying a payload in its namespace
(`extra["chariot.dice-tray"]`); its renderer claims exactly the messages matching that namespace.
Backend and frontend coordinate through data only.

The same shape-matching builds **four** things: the Provider swap list, "which renderer applies",
"which features are attachable", and "which pipelines a given event can trigger". One mechanism,
four uses — worth presenting as one in the docs.

**It is also a load gate.** The match resolves against data core already has, so "does this
renderer apply" is answerable *before any fetch*. A chat with no dice-tray messages never
downloads the dice-tray bundle. Build the loader match-first; the obvious implementation order
does it backwards.

## 7. Trust model

- **Admin-installed trusted code with server privileges** — the Obsidian/SillyTavern model, stated
  plainly in docs.
- **SDK-mediated access is enforced at runtime** against the hash-verified manifest and the
  admin's grants (F28). **Arbitrary code in hooks is not sandboxed** — a plugin can still touch
  the network or filesystem outside the SDK. What it cannot do is reach core data, another
  plugin's data, or another plugin's exports without a granted permission. State both halves.
- Users hold their own line: they may block a plugin from writing their data and must consent to
  anything affecting their account, but cannot block reads (11-EVENTS §4). This is enforceable
  precisely because the executor owns every Consumer invocation — the clearest payoff of the whole
  architecture.
- **Hard limits regardless of grants:** no plugin may modify user accounts, gate access to the
  application or its core loop, or hold user data hostage. Core's default chat pipeline is always
  available and cannot be removed (F29).

## 8. Storage lanes

1. **Namespaced `extraJson` on existing entities** — shipped today (character-card seeding uses
   it); sits under the `storage` capability.
2. **`plugin_data`** (plugin_id, key, value jsonb) — namespaced KV, in 0.6. Free-form JSON,
   any number of rows, referencing any entity id the pipeline has in hand:
   `.consume(save message → id)` then `.consume(save annotation referencing that id)`.
   Plugin-owned rows referencing a user's entities are the plugin's data and are cleared on
   uninstall (09 §7).
3. **Own file-based dataset or SQLite** in the extension's data directory, via custom hook or
   Consumer code. In-process Consumers may run custom commit code against extension-owned storage
   only.
4. **Own Drizzle table** — `contrib/` only; documented as core-power and throwaway.

**No *free-form* secrets column** — but a **typed `secret` settings field**, ruled 2026-08-18
(13 §6). Encrypted at rest with the app secret, write-only in the UI, delivered only into the
declaring extension's own hook invocation context, never readable through the SDK data API, never
recorded in a receipt, never exported.

The earlier "SP declines custody entirely" position is narrowed rather than reversed, for two
reasons found by writing it out:

- **Declining custody produced the worse outcome.** An extension keeping credentials in its own
  data directory has no key and no crypto facility, so the realistic result is plaintext on the
  user's disk — unencrypted *and* unauditable.
- **Free-form loses the enforcement.** If the column is opaque JSON, core cannot tell a secret from
  a note, so it cannot mechanically redact it from receipts (F16), exclude it from export (12 §7),
  or keep it write-only. A declared type makes all three enforceable by the mechanism that already
  protects connection material.

F18 is untouched: extension adapters still never receive core connection data, and core still never
sees a plugin's credentials for anything other than storing the ciphertext.

Never: raw Drizzle against core tables from plugins; plugin migrations on core schema.

## 9. Conformance kit

**Two kits, two audiences, and conflating them is how one of them ends up unused.**

| | `@serene-pub/conformance` | `@serene-pub/sdk/testing` |
|---|---|---|
| asks | *does this host obey the laws?* | *does my hook behave, and did my change alter what gets sent?* |
| run by | SP Core, and any alternate host | plugin authors |
| shipped to | core, not plugins | plugins |

The author-side half is the one that keeps a plugin working across SP releases, and it answers with
**goldens** rather than a pass/fail: record a receipt now, compare later, see the diff. *"It still
runs"* is not the assertion anyone needs — a plugin that runs and quietly changes the prompt is the
failure mode that reaches users. Goldens exclude timings on purpose; a golden that fails because a
run took 3ms instead of 2ms is a golden nobody keeps.

Alongside them, five **binding probes** state what a hook has to do to be a hook: return a
discriminated result rather than a bare value, reach for no services if it is a Task, take its
randomness from the run seed, settle rather than hang, and honour the abort signal. Each failure
names *what it breaks* — not just what it was — because an author reading "B3 failed" needs to know
that an unreplayable dice roll is one nobody can dispute.


Ships in SDK `/testing` beside the golden harness:

- **Binding conformance** — shape validation, discriminated-result behavior including `halt`,
  purity probes (a Task binding attempting service access fails loudly), randomness only via the
  run seed.
- **Surface conformance** — mount/update/destroy cycling, prop-schema fuzzing, leak checks on
  destroy, **p95 mount time under a threshold**, error reporting through `ctx` (10-COMPONENTS
  §7), contrast-token usage.
- **Equivalence** — forced-sequential async blocks and maps produce identical results (F26);
  a recorded stream replayed as a single value produces identical results (F16).

"Works as a surface/binding" is provable in an author's CI, not discovered in issue reports.
