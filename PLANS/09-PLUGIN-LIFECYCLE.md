# 09 — Plugin Distribution, Permissions and Lifecycle

**Status:** New, consolidated 2026-08-17. Split out of 03 so that doc stays about what an
extension *is*. Implements F27–F29. Distribution mechanics are 0.7; the manifest and permission
model are 0.6.

## 1. Umbrella terms

**Plugin** = a distributable package. Three mixable types: **extension** (code), **component**
(UI), **pipeline bundle** (static specs). The SDK packages all three.

## 2. Release standard

Repository-driven. SP maintains an official list; custom repositories can be added.

**Curation carries what mechanism shouldn't.** A plugin requiring extensive manual setup outside SP
is unlikely to be accepted onto the official list; a user who wants it badly can find the
repository and add it as a custom repo in the plugins sidebar. This is the right division: the
technical layer stays permissive and *verified* — declare a host requirement, or fetch a
checksummed dependency — while quality is enforced by listing policy rather than by a rule that
would have to guess where "too much setup" begins. It is also how Obsidian and VS Code handle the
same problem.

- **Only tagged releases are respected**, and the tag name must equal the manifest version.
- **The manifest is read from the commit the tag points at** — not a branch, not the artifact
  alone.
- Releases list with latest auto-selected; a toggle reveals pre-releases.
- The selected release renders its manifest details **before** install.

### Manifest fields

| Field | Note |
|---|---|
| `id`, `version` | version must equal the tag |
| `title`, `description`, `author`, `repository`, `website` | display strings are locale maps (04 §7) |
| `instructions` | **required** — how to use the plugin |
| type flags | extension / component / pipeline bundle, or any mix |
| `runtime.entry` | built JS entry, for extensions |
| build directory, spec export dir, component dir | per type |
| **artifact name per supported platform** | no programmatic guesswork in SP |
| **checksum per artifact** | named artifacts remove guesswork; hashes remove tampering |
| supported platforms | **load-bearing, not nominal** — artifacts differ because dependencies are bundled per platform (F33). An unsupported platform is refused at install with a clear message |
| declared host requirements | checked escape valve for things that cannot reasonably be vendored; verified at install, never presumed (03 §3) |
| `fetchedDependencies` | url + sha256 + size + platform + when. Displayed at install: *"will download ~400 MB from example.com on first use."* Undeclared fetching of executable code is a non-goal (03 §3) |
| `sdk.minimum` | minimum supported SDK version |
| `engines.serene-pub` | supported SP version or range — separate from the SDK range |
| `permissions` | generated by the SDK packager (§4) |
| hooks declared | ids and cadence |
| exports declared public | callable by other plugins |
| `dependencies` / `libraries` | runtime vs build-time — **never one field** (03 §2) |
| `adminOnly` | the plugin is an admin tool |
| `managesOwnCredentials` | surfaced at install: *"this plugin stores its own credentials; SP does not manage or protect them"* |
| declared bundle size | displayed at install (10 §10) |

**SDK tooling** composes the manifest, generates the permission list, and compiles
programmatically-defined pipelines into the static export SP imports (F27).

**A released plugin contains only compiled outputs** (04 §5a): pipeline documents, static UI
component files, one file per hook carrying its code, and whatever those hooks depend on. The
authoring source — the builder chains, the TS that declared the registrations — does not ship.

## 3. Verification chain

1. Tag → commit → manifest. Version must match the tag.
2. Artifact downloaded → checksum must match the manifest.
3. Manifest hash stored in `plugins.manifest_hash`.
4. Every runtime permission check validates against **that stored hash's** manifest (§5), which is
   what defeats tampering before or after build.

## 4. Permissions are generated, not authored — and that is a convenience, not a boundary

The SDK packager writes most of the manifest for the author (04 §5a). **Two mechanisms, two
reliability levels, and the manifest must distinguish them:**

- **Contributions** — hooks and their parameters, UI components, entry points — come from **static
  extraction** of registrations. Nothing is executed and nothing is discovered at runtime (F27),
  so the manifest says what the code says. Requires that registrations be statically analyzable
  (04 §5a).
- **Permissions** come from **static analysis** of call sites. This is an inference.

The rest of this section is about the second one.

**Say plainly in the docs that this is static analysis:** reliable for direct SDK imports,
defeatable by dynamic access, prone to false negatives. The generated list is a convenience and a
lint. **The runtime check (§5) is the actual enforcement.**

**The generator must walk vendored libraries.** A library's code runs under the host plugin's
identity (04 §2), so unwalked library calls are a permission-laundering path: either the runtime
denies calls the author believed were covered, or the blind spot aligns with a granted permission
and nobody notices. Each library's own permission set is listed separately at install so an admin
can see what came from where.

## 5. Install-time grants and the runtime double-check

**Install-time**

- Only permissions present in the verified manifest are toggle-able.
- **Nothing is granted automatically.** The admin toggles each on.
- An update requesting new permissions **does not inherit** a grant. The update flow shows a diff
  of what is newly requested.
- Permissions removed from a manifest are deleted from SP, so a stale grant can't sit there
  silently.
- Each permission is marked **required** or **optional**. Required and off → the plugin will not
  enable, stated at install. Optional and off → the plugin degrades and the SDK call returns
  `err(denied)`.

**Runtime — the double check (F28)**

Every SDK call, from a node binding or a hook, verifies:

1. the permission is present in the **hash-verified** manifest, **and**
2. the admin granted it on this instance.

Both must pass. Failure is `err(denied)` — routable and recorded, never a silent no-op.

**Performance:** resolve the effective permission set once per run and once per hook invocation
into an in-memory set. Never a DB read per call. The global switch (§8) is the outermost term of
that same set.

## 6. Activation and conflicts

**Activation is atomic.** A plugin shipping three pipelines where one conflicts activates none of
them — partial activation leaves an instance whose state matches no manifest.

"Any conflict" means, explicitly:

- a spec id already installed from a different source
- a spec id colliding with a core spec
- an older-version pipeline against an installed newer one (02 §4)
- same version, different canonical hash (02 §4)
- a pin to a type that isn't installed
- a declared dependency missing or out of its pinned range
- a `core:`-prefixed id from outside core (F2)
- an SDK-init namespace alias naming a different installed plugin's identity (04 §2)

Failures surface as the diagnosed broken state (§7), naming the specific conflict.

## 7. Directories, registration and lifecycle

```
<appdata>/plugins/extensions/     installed extensions
<appdata>/plugins/components/     installed UI components
<appdata>/plugins/data/<id>/      per-plugin data directory (plugin read/write)
```

Root configurable in SP settings; default overridable via `.env`. An extension has **read** access
to its own install directory and **read/write** to its own data directory. Nothing else.

- Plugins are registered in the database; files on disk are the payload.
- **Deleting a problematic plugin's files safely prevents load and decouples it from a live
  instance.** Decoupling works by the registry refusing to resolve it — in-flight work finishes or
  is cancelled, nothing new dispatches. **It is not a hot-unload**; already-imported code cannot
  be removed from a running Node process, and nobody should implement one.
- Admins see installed-but-broken with a **diagnosed cause** — files missing vs. a runtime error vs.
  a named conflict — never a bare "failed to load."
- **Controls:** enable, disable, stop, restart, at any time.
- **Uninstall** offers, individually: delete extension data rows, remove installed pipelines,
  delete the data directory. Plugin-owned rows referencing a user's entities are the plugin's
  data and may be cleared.
- **Core-table data is never touched by an uninstall.** Messages, characters and anything else a
  plugin's Consumer wrote into core tables survive — that data belongs to the user (F29). Specs
  pinning removed types fail validation and appear in `spec_diagnostics`.

## 8. The global plugin switch

**Plugins and the plugin sidebar are disabled by default**, enabled by an admin in system
settings. Disabled means surfaces unmount, nothing can be called, SP is instantly vanilla.

**Unmounting is the easy half.** "Can't be called" is enforced server-side at every entry point:

surface mounting · socket handler forwarding · lifecycle and scheduled hooks · plugin node
execution inside runs · exports called by other plugins · the `/api/plugins/:id/*` mount

- **Sessions bound to a spec that references any plugin fall back to core's default chat
  pipeline** while plugins are off, and restore their selection when re-enabled. The binding is
  preserved; only its resolution changes. This is what F29's never-removable core loop is *for* —
  the switch is only credible because that law exists.
- **In-flight runs are cancelled**, resolving `cancelled` and recorded. Letting plugin nodes finish
  after the admin hit the switch defeats the purpose.
- **Scheduled hooks don't fire while off, and missed firings are never backfilled** on re-enable.
- **Disabling is not uninstalling.** Tables, settings, data directories and installed pipelines
  persist untouched.
- **Toggling raises an admin notification and is recorded.** It is a global, security-relevant
  state change.
- Default-off means the zero-plugin bundle ceiling (10 §10) measures the common path, not an edge
  case.

## 9. Admin surface

The screens this design implies, listed so the information architecture is designed rather than
discovered: plugin list and install flow · granular permissions per plugin · pipeline list,
presets and configuration · connections across provider kinds · events registry and subscriptions
· notifications · budgets · diagnostics · the global switch · receipts and the run inspector ·
per-user consent overview.

UI can iterate, but **one behaviour must be right from the start:** an admin installs a plugin,
grants permissions, and *nothing happens to any user* until each user consents (11 §4). Without
clear messaging, admins will read correct behaviour as a broken install.
