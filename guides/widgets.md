# Widgets

A session's screen is made of **widgets**: the conversation, a portrait column, a stats panel. A
person places them in their session layout. Your plugin can add its own, and you have four ways
to get the look you want. Go only as far down this page as you need to.

1. **Restyle** an existing widget with CSS. No plugin needed.
2. **Write** a widget of your own: a component, and a widget that names it.
3. **Start from a core widget**: copy its source into your plugin and change it.
4. **Embed a document** inside your widget, for the one region that needs a real browser page.

## Restyle a widget

A widget style is CSS the app scopes to one widget. It changes colours, spacing and the message
layout, and needs no code at all. A person writes one in the layout editor's **Style** tab (see
[Session layout](/docs/session-layout#style)). Most changes stop here.

### Style parts

A style reaches inside a widget through its **parts**: stable names its elements carry in one
attribute, `data-widget-part`. An element can carry several, so select one with `~=`:

```css
[data-widget-part~="messages.message-avatar"] {
	border-radius: 0.25rem;
}
/* One widget's copy of a shared control, through its ancestor. */
[data-widget-part~="stats.root"] [data-widget-part~="stat-slot.bar"] {
	height: 0.5rem;
}
```

A part is `<owner>.<name>`. The owner is the widget that draws the element, by its widget id, or a
control several widgets share, by its own name (`stat-slot`, the stat control World State and
Stats both draw). A part names what an element is, never how it looks; state rides on the widget's
own `data-*` attributes (`data-msg-author`, `data-empty`), never in a part name. The parts core's
widgets draw today:

### Ship a style with your plugin

A widget declaration's `presets` are the built-in styles it ships. Each one is installed as a
style anyone can pick (and clone, but not edit) when your plugin is installed, updated or enabled,
and removed with it when it is uninstalled:

<!-- prelude:
import { widget } from '@serene-pub/sdk'
-->
```ts
const tray = widget({
	id: 'tray',
	title: 'Dice tray',
	component: 'tray',
	presets: [
		{ slug: 'default', title: 'Default', css: '' },
		{ slug: 'felt', title: 'Felt', css: '[data-widget-part~="acme.dice:tray.die"] { background: #2f5d3a; }' },
	],
})
```

`slug` is the style's stable name within the widget; keep it when you change the CSS, because a
saved layout finds its style by it. A preset you drop from the list is removed on the next update.

## Write a widget

A widget from scratch is a **component** (a module your plugin ships) and a **widget** that
names it. The CLI writes both for you:

```sh
serene-pub create component who-next --widget
```

This writes `components/WhoNext.svelte` and `components/who-next.ts`, and prints the two
declarations to add. Add `--vanilla` for plain DOM instead of Svelte. Components live beside
`src`, never in it: they run in the page, not in your plugin's sandbox, and `serene-pub build`
builds them separately.

<!-- prelude:
import type { GenreDecl } from '@serene-pub/sdk'
declare const myGenre: GenreDecl
-->
```ts
import { component, defineExtension, widget } from '@serene-pub/sdk'

// a widget names the component by slug; `genres` scopes it (absent = every genre)
export const whoNext = widget({ id: 'who-next', title: 'Who next', component: 'who-next', genres: [myGenre] })

export default defineExtension({
	slug: 'acme.who-next',
	name: 'Who next',
	version: '1.0.0',
	components: [
		component({ slug: 'who-next', label: 'Who next', entry: 'components/who-next.ts', framework: 'svelte' }),
	],
	widgets: [whoNext],
})
```

`serene-pub build .` compiles each component into one module under `dist/plugin/components/`.

An admin can also write a component inside the app (**Admin → Components**) without a plugin.
The same rules apply, and the same compiler builds it, but the in-app editor does not
type-check. For anything you mean to ship, use the CLI.

### What it is handed

A component gets one object, `ctx`. It holds what the session sent the widget, and the verbs
that act on the session:

```svelte
<script lang="ts">
	import type { ComponentContext } from '@serene-pub/component-client'

	let { ctx }: { ctx: ComponentContext } = $props()
	let count = $state(ctx.messages?.length ?? 0)
	$effect(() => ctx.subscribe(() => (count = ctx.messages?.length ?? 0)))
</script>

<p class="text-sm">{count} messages</p>
<button type="button" class="btn preset-tonal" onclick={() => ctx.invoke('advance')}>Continue</button>
```

| On `ctx` | What it is |
| --- | --- |
| `session`, `messages`, `channels` | The session, its messages, and each channel the widget declared. |
| `settings` | This widget's settings, defaults filled in. |
| `annex` | The session annex, holding only the keys this viewer may see. |
| `actions` | The actions the session offers, per venue. |
| `turnOrder`, `viewer`, `locale`, `theme`, `layout` | Who speaks next, who is looking, their language, the theme, and where the widget sits. |
| `scoped`, `grants`, `granted(scope)` | Extra data an admin granted (below). |
| `state` | The view state the widget saved last time. |
| `subscribe(fn)` | Called with a section's name whenever one changes. |
| `onEvent(fn)` | Called with each session event: a message created or updated, an event recorded. |
| `invoke(key, args?)` | Presses an action by its key. |
| `request(kind, params)` | Asks the page for something: open a character, page through messages, show an image. |
| `saveState(state)` | Keeps a little view state (a scroll position, an open tab) for the next mount. |
| `t(text)` | Your English text in the viewer's language, when the app has it. |
| `error(message, fatal?)` | Tells the page something broke. |

A press that changes something needs a person behind it: a click the page saw in the last few
seconds. A press on load or on a timer is refused. Some request kinds (`send`, `draft`,
`fire-turn` and others) are for core's own widgets only, and a plugin's widget is refused them
with a sentence.

`ctx.locale` is the viewer's language code: pass it to `i18nText` to show a `{ en, … }` map in
the language the rest of the page speaks.

### Extra data an admin grants

Beyond the basics, a widget may ask for more of the session by declaring **scopes**:
`session:state` (stats and states), `characters` (the cast), `lore` (pages of the session's
lorebook entries), `session:full` and `persona`. Each scope arrives in `ctx.scoped` only once an
admin grants it, and an admin may refuse, or revoke it while the widget is open.

An absent section therefore means "not granted" or "not sent yet". `ctx.granted(scope)` tells
them apart: `true`, `false`, or `undefined` while the page has not said. Draw `false` as its own
state, never as loading, or a widget whose scope was refused waits forever:

```svelte
{#if ctx.granted('session:state') === false}
	<p>{ctx.t('This widget has not been granted the session\'s stats.')}</p>
{:else if !ctx.scoped.session_state}
	<p>{ctx.t('Loading…')}</p>
{:else}
	…
{/if}
```

### Where it runs

Not in the page. Your component runs in the page's **UI worker** (one per plugin per session
page) against a small DOM of its own, and the page **mirrors** what it builds. Three things
follow:

- **You place host elements.** Plain HTML (`div`, `p`, `button`, `input`, `a`, `img`, lists,
  tables) and the `sp-*` set (`sp-popover`, `sp-menu`, `sp-tabs`, `sp-dialog`, `sp-combobox`,
  `sp-message-body`, `sp-scroll`, `sp-frame` and the rest), which the page draws with its own
  controls, so they look and behave like the app's. Anything else is dropped before it reaches
  the page, and so is any attribute the element does not take. `@serene-pub/sdk/host-elements`
  has the typings. Plain elements take the accessibility attributes: `role`, `aria-label`,
  `aria-labelledby`, `aria-describedby`, `aria-hidden`, `aria-current`, and `aria-live` (`off`
  or `polite`). A widget never takes `aria-live="assertive"`: it would interrupt the
  screen reader, and the page keeps that for its own alerts.
- **You style with classes.** The app's utility classes work, but only the ones the app's own
  code already uses: the stylesheet is generated when the app is built. A class nothing in the
  app uses does nothing, silently. A `<style>` block is dropped at build.
- **No network.** `fetch`, sockets and storage do not exist in the worker, and an image is the
  app's media or your plugin's own file, never another host. Your data arrives on `ctx`;
  anything from outside comes through your plugin's pipelines.

### Which sessions offer it

Your **plugin** declares its widgets; a **genre** decides what its sessions leave out and how
they are laid out.

- A widget with `genres: [someGenre]` is offered in those genres' sessions only; without
  `genres`, in every session. Either way it waits in the layout editor's tray until someone
  places it.
- A genre withholds any package's widgets, core's included, by value:
  `omitWidgets: [coreWidgets.stats]` (`coreWidgets` comes from `@serene-pub/core-catalog`).
- A genre ships its layouts: `layouts: [layout({ slug: 'default', name: 'Board', preset })]`.
  The first is its default. `preset` is a **session layout** (`SessionLayoutV1`), the same
  format a person arranges; see below.
- A person may place any widget in any zone, as many times as they like. A widget that must
  exist once (it holds global state) declares `maxInstances: 1`.
- A genre that withholds the conversation (`omitWidgets: [coreWidgets.conversation]`) must place
  the widget that stands in for it in the layout it ships first, and that widget declares
  `role: 'primary'`, so a session always keeps one. The build refuses the package otherwise.
  Battleship does exactly this: its board stands where the conversation would.

A layout names your widgets by their `id` and core's by theirs:

<!-- prelude:
import type { SessionLayoutV1, WidgetDecl } from '@serene-pub/sdk'
declare const board: WidgetDecl
-->
```ts
const preset: SessionLayoutV1 = {
	widgetGrid: {
		version: 1,
		cell: 44,
		widgets: [
			{
				id: board.id,
				zone: 'middle',
				order: 0,
				size: { w: 'grow', h: 'grow' },
				anchor: { top: true, bottom: true, left: true, right: true },
			},
		],
	},
	zoneLayout: { version: 1, zones: { right: { kind: 'side', side: 'right', widgets: ['stats'] } } },
	widgetSettings: { [board.id]: { zoom: 'fit' } },
}
```

`widgetGrid` places widgets in a zone, `zoneLayout` lists a side's widgets, and `arrangedGrid`
gives them whole cells. `widgetSettings` and `widgetStyles` carry the values and styles that come
with the layout. A zone is keyed by where it is drawn: `left` or `right` for a side, `top` or
`bottom` for a strip. A second copy of a widget is `<id>#<name>` (`messages#sanctum`), and its
settings are keyed the same way. `layout()` checks the layout where you declare it, so a widget
placed in two zones fails the build, not a session.

### Carded or flush

A widget placed in a session sits **flush** in its cell: the page draws no card around it, and
your own style decides whether it has a surface. The page draws a card (a surface, a border and
a title bar) when the person turns on the widget's **Card** setting, and always while the widget
is opened over the session for a moment: a pop-over, a flyout, the phone's panel sheet.

So a widget that paints its own backdrop should leave it off while the page is carding it, or
the two stack. `ctx.layout.chrome.card` says which it is:

<!-- prelude:
import type { ComponentContext } from '@serene-pub/component-client'
declare const ctx: ComponentContext
declare const root: HTMLElement
-->
```ts
import type { LayoutV1 } from '@serene-pub/sdk'

const carded = () => (ctx.layout as LayoutV1 | undefined)?.chrome.card ?? false
const paint = () => root.classList.toggle('my-widget-surface', !carded())

paint()
ctx.subscribe((section) => {
	if (section === 'layout') paint()
})
```

The page also marks the widget's box with `data-sp-card="on"` or `"off"`, for a style that would
rather key a rule off it.

### Testing it

`@serene-pub/cli/testing` mounts a component the way a session page does (built by the same
bundler, run in a worker by the same runtime) with a context you hand it, and gives you the DOM
the page would show:

```ts
import { test, expect } from 'vitest'
import { mountComponent } from '@serene-pub/cli/testing'

test('shows the count and continues', async () => {
	const view = await mountComponent({
		entry: 'components/who-next.ts',
		context: { messages: [{ id: 1, role: 'user', content: 'Hi' }] },
	})
	expect(view.query('p')?.textContent).toBe('1 messages')
	await view.click('button')
	expect(view.invoked).toEqual([{ key: 'advance' }])
	expect(view.refused).toEqual([]) // nothing the page would drop
	await view.unmount()
})
```

- **Acting as a person.** `click`, `input`, `check`, `pressKey` and `dispatch` act as a person
  would, and each waits until the component has finished answering. Work the component schedules
  for later (a timer, an awaited call) is yours to wait for: `settle()` waits again.
- **Changing what the page sent.** `push(section, value)` changes a section, `event(e)` delivers
  a session event, and `setGrants([...])` changes the widget's scopes as an admin's review would.
- **What went wrong.** `refused` lists anything the page would drop (an element, an attribute, a
  value). `refusedInvokes` lists presses refused because no person was behind them.
  `errors` lists what the component reported or threw.

The harness holds your component to the page's rules:

- **`reads`.** Pass your declaration's `reads` (`reads: myWidget.reads`). A section it does not
  name is never sent, as on the page.
- **The person gate.** A press that changes a message (`hide`, `retry`, `extend`, `delete`,
  `edit`, `swipe`) passes only within five seconds of a person's `click`, `pressKey`, `input` or
  `check` in the widget. `invokeGate: false` records every press, for a test that only cares
  about the call.
- **Ids.** Every `id` (and `for`, `aria-*` reference, `#fragment` and control `name`) is prefixed
  per widget, so a component never names one of the page's elements. Match elements by class or
  tag, or by `` `#${view.idPrefix}name` ``.

What the page does that the harness does not: it draws `sp-*` elements with the app's own
controls (here they stay as they are, attributes and children intact), and it asks the person
to confirm a widget's `retry`, `extend` or `advance`, and a plugin widget's `edit`.

Run the test in a DOM environment (vitest's `environment: 'happy-dom'`), or install `happy-dom`
and the harness brings its own.

## Start from a core widget

A clone starts from core's own source instead of an empty file. `serene-pub clone` copies a core
component into your plugin:

```sh
serene-pub clone --list                 # what can be copied
serene-pub clone stats --as party-stats # components/party-stats/, paths kept
```

It writes every file under `components/<as>/` with the path it has in core (so the copy diffs
against core file for file), plus a `based-on.json` recording what it copied. It refuses to
overwrite a file that is already there (`--force` overwrites), and it prints the `component(…)`
and `widget(…)` declarations for you to paste. `--as` defaults to `my-<slug>`, and it cannot be a
core component's slug.

**A copy is a plugin's widget.** Core's widgets can do things a plugin's cannot. `clone` prints
what the copy will lose: the request kinds only core's widgets may ask (`send`, `draft`,
`fire-turn`, …), `<sp-host-view>`, and `autofocus`. The printed widget declares the scopes the
source reads, which an admin reviews at install. Copying `messages` (the conversation) keeps the
log and loses the composer and sending; `clone` warns you and lists what goes.

When core changes, `serene-pub drift` says so:

```sh
serene-pub drift .
# ⚑ party-stats (from core's 'stats'): core moved on — you copied 7a2ef1b424f9, core is …
#     changed sessions/stats/StatsWidget.svelte   ← you edited it too: merge by hand
```

It lists the files core changed, added or removed since your copy, and marks the ones you edited
too. It exits 1 when core moved on, so a CI step can say so.

## Embed a document

For the one region that needs a real browser page (a charting library that measures, a rich-text
editor, artwork drawn with its own CSS) place an `sp-frame` inside your component:

```svelte
<sp-frame src="ui/chart.html" title="Chart" props={JSON.stringify({ points })} oninvoke={invoke}></sp-frame>
```

The page loads that document, which your plugin ships, in a sandboxed frame. The document
receives `props`; when a person presses something in it, it sends `invoke`, which reaches your
component as the element's `invoke` event. Pass it on with `ctx.invoke(detail.key, …)`: a
person's press inside the document counts as a person behind your component's press.

`serene-pub create component <slug> --embed-document` adds one, with its document
(`ui/<slug>.html`) and the script beside it. Twenty Questions' Tally is a worked example. The
document's rules are in [Frames](frames.md).
